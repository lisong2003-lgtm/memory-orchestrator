# 提示词：安装后对“已有对话框”自动做一次全量检测并提醒

> 用途：交给负责改造 codex-memory-orchestrator 的 Agent。前提是上一版「任意 Agent 实时轮数提醒」已落地（agent_hook.sh / state.py）。本提示词只解决：**用户安装该 Skill 之前就存在的老对话框，在安装后要自动全量检测一次，找出超阈值者并自动提醒**。

## 一、任务目标（可验收）

1. Skill 安装完成后，自动执行**一次全量存量检测**：扫描用户机器上所有**安装前已存在**的对话框（本机可读会话目录），统计每个对话框的累计用户轮数。
2. 只统计轮数、不记录内容、不上传网络。
3. 按设定阈值分组输出自动提醒：
   - **已超阈值**（hard，默认 `>=8`）：列出对话框，提示“先生成恢复包，再开新对话”；
   - **接近阈值**（提前 1 轮，默认 `>=7` 且 `<8`）：列出对话框，提示“再 1 轮将达到阈值，请准备开新对话”。
4. 提醒可被“已提醒”标记抑制：同一对话框只提醒一次，重复扫描不刷屏。
5. 全量检测结果写入 `state.json` 的 `index`（兼容现有 monitor_dialogs.py 的 `--write-state` 结构），供后续恢复包登记与下次扫描去重。

## 二、现状核查（已读数）

- `scripts/monitor_dialogs.py` 已有：按 `rollout-*.jsonl` 的 `item_completed.UserMessage` + `turn_id` 去重统计轮数；`--threshold/--warn-at/--days/--write-state/--json`；已有 over/warn 分组与“已超阈值/接近阈值”输出。
- 缺口：`--days N` 是“最近 N 天”过滤，`--days 0` 会因 `cutoff=now` 而扫不到任何文件；**目前没有“全量扫描全部历史对话框”的模式**，也没有安装时一次性自动触发的入口。

## 三、实施建议（供确认，不在此步骤改码）

1. `monitor_dialogs.py` 新增 `--all` 参数：`--all` 时关闭 mtime 过滤，全量扫描 `sessions/**/rollout-*.jsonl`；`--all` 与 `--days` 互斥（同时指定时报错）。
2. 新增只读的存量标记字段：`state.json` 的 `index` 里给每个 session 加 `over_warned`/`installed_baseline_checked` 时间戳，供“已提醒不重复”用。
3. 安装脚本/说明新增一步：
   ```sh
   python3 <skill>/scripts/monitor_dialogs.py --all --write-state --json
   ```
   把返回的 `warn_sessions` / `over_sessions` 直接转成用户可读的自动提醒；同时登记一条 `last_full_scan`（`YYYY-MM-DD HH:MM` + 扫描文件数与命中数）到 state.json。
4. 提醒文案（示例，用中文、一次输出清楚）：
   - 超阈值：`🔴 对话框《标题》已达 N 轮（阈值 X）：请先生成恢复包（scripts/recovery.py --add 项目 路径），再开新对话。`
   - 接近阈值：`⚠️ 对话框《标题》已达 N 轮：再 1 轮将到阈值 X，请准备开新对话。`
   - 无命中：`✅ 安装后全量检测完成：未发现超阈值/接近阈值对话框。`
5. 安装后如何自动触发：把“安装本 Skill 后的首轮运行”作为安装步骤写进 SKILL.md / README / 平台发布说明；macOS/桌面环境可用一次性 heartbeat 任务（仅跑一次，写完 `last_full_scan` 后标记完成），Windows 用一次性 `schtasks`，Linux 用一次性 `at`/手动首跑。不强制用户手工。

## 四、能力边界（必须向用户明示）

- 全量检测只覆盖**本机可读的 Codex 会话 rollout**；已删除/已清理/加密/远端 host 上的老对话框读不到，就无法检测（如实说明，不臆造）。
- `rollout` 只用于统计轮数，不读对话正文；SQLite catalog 仅用于关联标题/项目名。
- 只做“检测+提醒”，不在此步骤自动生成恢复包或自动关闭旧对话；超阈值对话框仍按既有规则手动/辅助生成恢复包。
- 不做任何网络请求；发布版不包含上报逻辑。

## 五、风险

- R1：老 rollout 文件量大 → `--all` 首次扫描可能耗时；提示监控输出“扫描 N 个文件”，超过 3 分钟可接 `--json` 分段或加交互进度，不阻塞。
- R2：同一对话框重复提醒刷屏 → 用 `installed_baseline_checked` + `over_warned` 标记，同一阈值只提醒一次。
- R3：`--all` 与既有 `--days` 契约冲突 → 明确互斥参数并更新 self_test。
- R4：SQLite 不可用 → 保持现有降级（用文件名/thread_id 展示），不阻塞检测。
- R5：滚动窗口计数与真实累计轮数口径不同 → 维持现有 UserMessage+turn_id 口径，不做新定义。

## 六、验证计划（改完必须跑）

1. 造 3 个假 rollout（8 轮 / 7 轮 / 3 轮）放在临时 `--sessions-dir`，跑 `monitor_dialogs.py --all`：必须稳定输出 over=1、warn=1。
2. 同批次验证：默认（不带 `--all` 且 `--days` 很大）不应误报全量；`--all --days 1` 必须报参数冲突退出非 0。
3. 跑两次 `--all --write-state`：第二次不再重复提醒（靠标记去重）。
4. `state.json` 的 `index` 含 `scanned_files/last_full_scan/sessions[i].over_warned` 且不含任何对话正文字段。
5. 回归：现有 15 项 self_test 全绿；grep 核心脚本无 `socket|requests|urllib|http` 引用。
6. 真实机条件：在本机运行一次 `--all`（只读统计），确认输出正常且不联网（可用 `lsof -i` 抽查进程无出站连接）。

## 七、不做什么（防范围蔓延）

- 不做云端同步、不写内容摘要、不记录正文。
- 不承诺检测到本机读不到的远端/云对话框。
- 不在这一版改 agent_hook.sh 的实时自检逻辑（两者互补：安装时全量扫存量，运行中实时增量）。
